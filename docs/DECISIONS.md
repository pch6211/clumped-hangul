# 아키텍처 결정 기록 (ADR)

각 항목은 "맥락 → 결정 → 이유 → 대안"을 짧게 남긴다. 번복 시 새 항목으로 갱신.

---

## ADR-001 — 빌드 스택: Vite + TypeScript(점진), React 미도입
- **날짜**: 2026-06-13
- **결정**: Vite를 번들러/개발서버로, TypeScript를 점진 도입(`allowJs`). React/Next는 쓰지 않음.
- **이유**:
  - 이 앱의 본질은 canvas + requestAnimationFrame 렌더 루프 + 물리 시뮬레이션. React의
    가상 DOM은 canvas 그리기에 이점이 없고 렌더 루프와 충돌. Next의 SSR/라우팅도 불필요.
  - 노드·엣지·본드·모임꼴 박스 등 복잡한 공유 상태에 타입을 입히면 리팩터링·신기능이 안전해짐.
  - Vite는 HMR과 단일 번들 산출로 기존 GitHub Pages 배포와 호환.
- **대안**: 순수 JS 유지(타입 안전망 없음) / React 도입(canvas 코어엔 부적합, 비용 큼).

## ADR-002 — 데스크탑 앱: Electron (Tauri/Swift 아님)
- **날짜**: 2026-06-13
- **결정**: 데스크탑 버전은 Electron으로. 같은 Vite 번들을 웹/데스크탑이 공유.
- **이유**:
  - **렌더링 일관성**이 핵심. Electron은 항상 동일 Chromium으로 그려 개발(크롬)과 1:1.
    이 앱은 커스텀 canvas·블러 필터·SVG/폰트 익스포트 등 렌더 민감 작업이 많음.
  - Tauri는 OS 시스템 웹뷰(Mac=WKWebView/사파리)라 canvas·필터·폰트 렌더가 OS별로 다를 위험 +
    Rust 툴체인(rustup/cargo/Xcode CLT) 추가 부담.
  - Swift 네이티브는 JS 자산을 버리게 되어 "웹·데스크탑 동시 유지"와 모순.
- **대안**: Tauri(초경량 ~10MB이나 렌더 편차·Rust 부담) / Swift(풀 재작성).

## ADR-003 — 모노리스 분할: 안전 점진 방식
- **날짜**: 2026-06-13
- **결정**: 13k줄 단일 index.html을 한 번에 쪼개지 않고, ① 먼저 Vite 도입(코드 무변경) →
  ② 인라인 스크립트를 `src/main.js` 단일 모듈로 추출(동작 보존) → ③ 이후 기능 클러스터를
  하나씩 분리(추출마다 커밋+브라우저 검증). 너무 얽힌 클러스터는 감싼 채 두고 "리뷰 필요" 표시.
- **이유**: 전역함수 313개·공유 전역상태가 많아 일괄 분할은 깨지기 쉬움. 단계별 검증으로
  회귀 지점을 특정 가능.
- **검증**: 각 단계에서 `npm run build` + 실제 Chrome 렌더(콘솔 에러 0, 캔버스 픽셀) 확인.

## ADR-005 — 배포: 당분간 현행 유지, 빌드 파이프라인은 나중에 전환
- **날짜**: 2026-06-13
- **결정**: 라이브(clumped-hangul.com)는 `main` 루트 index.html 서빙 유지. Vite 빌드→Pages
  Action은 준비해 두되, `main` 머지 + Pages 소스 전환은 의도적 별도 단계로 미룸.
- **이유**: 작업은 `Jisung_01` 브랜치에 격리 → 라이브 사이트 무영향. 동작 보존 검증이 충분히
  쌓인 뒤 전환해야 안전.
